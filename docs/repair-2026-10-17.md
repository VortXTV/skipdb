# Read-only, resolved-cache and reputation repair candidate

SkipDB uses PostgreSQL 16 in its local compose file and Drizzle's node-postgres driver. This is not a D1 migration.

Read-only instances reject direct admin moderation/import/bulk, profile updates, API-key deletion and Auth.js handlers before actor/body processing. Raw Auth.js server-action exports also reject sign-in/sign-out; auth() returns null without invoking the database-session refresh path. Direct key creation/revocation and session creation helpers reject before crypto, cookies or database access. Cached metadata remains readable; a missing title returns 404 instead of inserting a placeholder. Metadata refresh/episode fills and API-key last-used touches do not write in read-only mode. Explicit operator import/seed commands remain separate maintenance operations; the resolved backfill uses the read-only-aware resolver and requires writable maintenance configuration.

The additive 0005 migration retains the complete legacy resolved_segments table. A new resolved_segments_current projection has one unique JSONB [imdbId, season, episode, segmentType] key. JSON null and numeric zero differ. Backfill selects latest updated_at then highest legacy id deterministically without deleting any legacy row. Runtime recomputation obtains a PostgreSQL transaction advisory lock before selecting approved candidates and atomically upserts the unique key; an empty group removes only its current projection. Segment id is the final deterministic winner tie-break.

Reputation changes use one contribution formula: score + reputationPerApproval when approved, score otherwise. Mutation transactions lock the source segment, update its state/votes, append audit evidence and atomically add only the contribution delta to its contributor. Repeated approval/vote requests add zero; rejection/edit-to-pending reverses approval credit; deletion removes that segment's current contribution. Approval creation, staff import, edits and resubmits use the same arithmetic. Existing reputation balances and historical logs are retained; past inflation or manual credits are not guessed or retroactively rewritten.

## Maintenance bootstrap and read-only refusal

The seed entrypoint loads dotenv/config before the resolver or database dependency, so a documented .env-only DATABASE_URL and read-only setting are available before either dependency evaluates. The db:resolve entrypoint explicitly refuses NEXT_PUBLIC_READ_ONLY=true before its first query, reports an actionable error and exits nonzero. It never silently clears or overrides the flag. For deliberate maintenance, pause application writers through the existing migration/code/import/rebuild cutover, verify the target database, and use NEXT_PUBLIC_READ_ONLY=false pnpm db:resolve only in the maintenance process. A mirror's serving environment stays read-only.
